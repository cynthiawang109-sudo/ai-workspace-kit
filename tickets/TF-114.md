# TF-114: Keep dependency and cache directories out of the doc-search corpus

- Project: ai-workspace-kit (mcp/doc-search)
- Status: open
- Priority: low

## Problem

`_iter_docs()` in `server.py` yields every Markdown file under
`projects/`, skipping only paths with a `.git` part. Checked-out
sub-repos carry generated directories - demo-app's `.venv`
(third-party package READMEs under site-packages),
`node_modules`, `__pycache__`, `.pytest_cache` - and their
Markdown is indexed by all three search modes and by the
embeddings index. The TF-113 evaluation made the cost visible:
baseline result lists contain hits from files that are not
workspace documentation at all, and the embeddings index spends
chunks on them. Flagged as a pre-existing issue by the TF-113
review; TF-113 deliberately kept the corpus unchanged so its
three-mode comparison stayed fair.

## Change

1. `_iter_docs()` excludes any path that has a part in a named
   exclusion set: `.venv`, `venv`, `node_modules`,
   `__pycache__`, `.pytest_cache`. The existing `.git`
   exclusion is folded into the same mechanism. The set is a
   module-level constant with a comment saying what belongs in
   it (dependency installs and tool caches - never content
   directories), so a future addition is a deliberate edit.
2. Nothing else changes: the corpus definition stays "the
   Markdown the workspace sync checked out under projects/",
   minus generated directories. All three search modes and
   the embeddings fingerprint see the same, cleaner corpus
   (the fingerprint changes once, so the index rebuilds on
   first use after this lands - expected, not a bug).

## Acceptance

- New tests: a fixture workspace with Markdown inside
  `.venv/`, `node_modules/`, and `.pytest_cache/` directories
  returns no hits for those files from any of the three
  search modes, while real docs still rank as before.
- All existing tests keep passing.
- On the maintainer's real workspace, the corpus file count
  before/after is recorded in the resolution, and the TF-113
  evaluation is re-run and appended to EVAL.md as a dated
  second run (the first run stays, labelled pre-TF-114).
