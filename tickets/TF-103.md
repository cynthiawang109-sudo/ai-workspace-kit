## Problem

The worker's digest job retries on failure without logging the attempt
count, and a retry after a partial send can deliver the digest twice. Per
`taskflow-docs/system-overview.md` the retry ceiling is 5 attempts before
dead-letter; the job should log each attempt with the user ID (never the
email address — PII rule) and make sends idempotent per week.

## Resolution (2026-11-12, demo-app PR #4, merged)

Implemented in demo-app (`digest.py`, the worker's demo slice):

- A `digest_sends` ledger keyed by (user_id, week) — that pair is the
  primary key and the idempotency key handed to the sender; the table
  is applied by the pre-start migration, and its PII story is
  documented in `taskflow-api-docs/data-model.md`. Recipients are
  identified by user ID only; there is no email column.
- Every attempt is reserved (SQL-side increment, committed before the
  send), logged with the user ID, and failures store only a sanitized
  error code — never the exception message, which can carry PII.
- Retries use bounded exponential backoff inside the persisted
  5-attempt budget; at the ceiling the row is dead-lettered and later
  runs leave it alone. Diagnosis and reset steps are in
  `taskflow-docs/incident-runbook.md`.
- The sender contract is atomic dedupe on the idempotency key (the
  demo `OutboxSender` locks its outbox file), so a partial send or
  overlapping runs cannot deliver twice — pinned by a concurrency
  test with the real sender.

Reviewed via the review-pr skill (request changes: PII in error
diagnostics, concurrent double-delivery, missing backoff, suppressed
CLI logs, missing runbook — all addressed). 26 tests pass on merged
main.
