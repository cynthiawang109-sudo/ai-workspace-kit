# TF-113: Real embeddings for doc-search (third rung of the retrieval ladder)

- Project: ai-workspace-kit (mcp/doc-search)
- Status: open
- Priority: medium

## Problem

doc-search has two retrieval modes and both are bag-of-words:
`search_docs` (hand-weighted keyword counts) and
`search_docs_semantic` (TF-IDF cosine). The README says so
honestly: neither understands synonyms, so a query phrased
differently from the documents ("what happens when a job keeps
failing" vs. the docs' "dead-letter after 5 attempts") can miss
the right page entirely. The retrieval ladder's third rung -
real text embeddings - is missing, and there is no measurement
comparing the three modes.

## Change

1. **New tool `search_docs_embeddings(query, limit=8)`** in a
   new module `embeddings.py` beside `server.py`; existing
   tools are not renamed or changed. Same result shape as the
   other searches (path, title, score, snippet) plus a
   `heading` field naming the matched section.
2. **Indexing**: the corpus is the same one the other tools
   search (`_iter_docs()` under `projects/`). Documents are
   split into chunks at ATX headings (a chunk is a heading
   trail plus its body; the preamble is a chunk under the
   document title). Chunk embeddings are stored in
   `mcp/doc-search/.index/` (`chunks.jsonl` + `manifest.json`
   with the model name and a content-hash fingerprint of the
   corpus). The index rebuilds automatically when the
   fingerprint or model changes. `.index/` is gitignored.
   Cosine similarity is computed in pure Python stdlib - at
   documentation scale (hundreds of chunks) this is deliberate,
   and it keeps the base install dependency-free.
3. **Embedder**: `sentence-transformers` with
   `sentence-transformers/all-MiniLM-L6-v2`, imported lazily
   and listed only in a new `requirements-embeddings.txt`
   (the base `requirements.txt` and CI stay untouched and
   torch-free). The model name is overridable via
   `DOC_SEARCH_EMBEDDING_MODEL`. Without the optional
   dependency the tool raises a clear error naming the install
   command. Everything runs locally; the only network use is
   the one-time model download, and the README's "no network"
   bullet is corrected to say exactly that.
4. **Testability**: `DOC_SEARCH_EMBEDDER=fake` selects a
   deterministic test embedder (hashed token bag, normalized),
   so unit tests exercise chunking, indexing, staleness, and
   ranking with no model download. The tool is annotated
   read-only like the other searches; the docstring and README
   disclose the one side effect - writing the derived index
   cache inside the server's own `.index/` directory.
5. **Evaluation**: `eval/queries.json` holds ~12 queries with
   expected documents, tagged exact / paraphrase / synonym.
   `scripts/run_eval.py` runs all three search modes over the
   set and reports hit@1 and hit@3 per mode; a real local run
   (real model) is written up in `mcp/doc-search/EVAL.md` with
   the model name and date. The eval is not run in CI.
6. **Docs**: README gains the third tool row, the comparison
   section becomes the three-rung ladder, and Setup documents
   the optional embeddings install.

## Acceptance

- Existing tests pass unchanged; new tests (fake embedder)
  cover chunk splitting, index build + search ranking,
  staleness rebuild on corpus change, and the result shape.
- A real-model smoke on the maintainer's machine: a synonym
  query with no shared content words ranks the expected
  document first via `search_docs_embeddings` where TF-IDF
  does not.
- `EVAL.md` records the three modes' hit@1 / hit@3 from a
  real run, whatever the numbers are.
- CI (`doc-search tests`) stays green and does not install
  torch.
