# TF-110: Pin sub-repo versions — reproducible sync

- Project: ai-workspace-kit (workspace tooling)
- Status: open
- Priority: medium

## Problem

`sync.sh` / `sync.ps1` clone or fast-forward each sub-repo to the
tip of its `main` branch. Two runs on different days can assemble
different workspaces, and there is no record of which combination
of sub-repo states was last verified together (by the test suites,
the reviewers, and doctor). Rebuilding the workspace from the main
repo alone is not reproducible.

## Change

1. **New manifest `versions.txt`** at the workspace root, one
   `<name> <full-sha>` line per repo in `repos.txt` order, with a
   header explaining: pins are the `main`-branch SHAs of the last
   verified combination; demo-app releases are tagged in demo-app
   itself and are orthogonal to these pins. Every repo in
   `repos.txt` must have a pin; a missing pin is an error.
2. **Sync materializes the pins.** For each repo:
   - Missing checkout: clone, then check out the pin (when the pin
     equals the remote `main` tip, the clone is already there and
     stays attached to `main`; otherwise the checkout is detached
     at the pin).
   - Existing checkout with uncommitted changes: warn and skip —
     sync never clobbers local work (existing rule, kept).
   - Existing clean checkout: fetch; if HEAD already equals the
     pin, no-op (reattaching to `main` when the pin is the `main`
     tip and the checkout is detached); if the pin is the remote
     `main` tip, check out `main` and fast-forward to it; otherwise
     check out the pin (detached).
   - A repo whose pin is missing from `versions.txt`, or whose pin
     cannot be checked out, counts as failed (exit 1), as today.
   - The `-Only` / substring filter keeps working, for both normal
     sync and pin updates.
3. **Pin bumps are deliberate.** `sync.sh --update-pins` /
   `sync.ps1 -UpdatePins` fetch each repo and rewrite its pin to
   the current remote `main` SHA, printing which pins changed. The
   bump takes effect for other machines when the updated
   `versions.txt` is committed to this repo — that commit is the
   reviewable act. Updating pins does not move checkouts.
4. **Doctor verifies the pins.** New "pinned versions" section in
   `doctor.sh` / `doctor.ps1`:
   - `versions.txt` missing, or a repo without a pin: fail.
   - HEAD equals the pin: ok.
   - HEAD differs while on a feature branch: warn (development in
     progress).
   - HEAD differs on `main` or detached: fail, naming both SHAs
     and the remedy (`./sync.sh`).
   - The existing git-state section treats a detached checkout
     whose HEAD equals the pin as ok ("detached at pin") instead of
     warning about the branch.
5. **Docs.** README gains a short "Reproducible sync" section
   (what the pins are, sync semantics, how to bump). `AGENTS.md`
   gains one conventions line: after merging sub-repo work, bump
   the pins and commit `versions.txt`.

## Out of scope

- Tagging the sub-repos themselves, or pinning by tag.
- Changing how the main repo itself is versioned (the manifest
  commit is its version).
- Any change to sub-repo contents.

## Acceptance

- A fresh clone of this repo followed by `./sync.sh` materializes
  every sub-repo at exactly its pinned SHA.
- Moving one checkout off its pin makes doctor fail with the pin
  message; running sync restores it and doctor passes again.
- A dirty checkout is warned about and left byte-identical by sync.
- `--update-pins` is idempotent when nothing has moved.
- On the current workspace (all pins at the `main` tips), sync is
  a no-op and doctor is fully green.
