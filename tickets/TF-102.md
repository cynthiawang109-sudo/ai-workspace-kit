## Notes

Profiling points at the board rendering every task card up front. First step
in progress: confirm the API side is paginating per the conventions doc
(cursor-based, `taskflow-api-docs/api-conventions.md`) before optimizing the
client — no premature frontend work.

## Resolution (2026-11-12, demo-app PR #3, merged)

Confirmed on the API side: list pagination existed, but `GET /v1/tasks` had
no status filter, so a board client had to download every task and group it
client-side — the up-front cost the profiling saw. Fixed in PR #3:

- Optional `status` filter on `GET /v1/tasks` (per-column cursor
  pagination), documented in `taskflow-api-docs/api-conventions.md`.
- `(status, id)` index, applied by the pre-start migration
  (`scripts/migrate.py`) per deployment.md §4 — not lazily mid-request.
- Pagination bounds clamped (recorded pre-existing issue).

Benchmark (`scripts/bench_board.py`, 60,000 tasks): board first paint went
from 60,000 items in 649.2 ms to 150 items in 5.8 ms; the filtered query
plan switched from a primary-key scan to the new index. Reviewed via the
review-pr skill (request changes → all findings addressed); 15 tests pass
on merged main. Remaining client-side rendering work is out of scope here,
as the ticket prescribed.
