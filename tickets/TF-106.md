## Problem

`taskflow-api-docs/data-model.md` defines comments as append-only: a
comment is never edited in place; an edit is a new revision row that
carries `supersedes_id` pointing at the revision it replaces. The
error catalog already reserves `comment_not_found` (404) and
`conflict` (409). demo-app implements none of this: its verified
surface is `/health` plus the three task operations, so the
comments model — the workspace's second documented resource — has no
running code behind it.

## Scope (demo slice, in demo-app)

- New `comments` table, applied by `migrate()` like every schema
  change here (pre-start, expand-only — never lazily at request
  time): `id`, `task_id`, `body`, `supersedes_id` (NULL for an
  original comment), plus an index on `(task_id, id)` for the
  per-task cursor walk, mirroring TF-102's board index.
- `POST /v1/tasks/{task_id}/comments` → 201. Body:
  `{ "body": "...", "supersedes_id": <int, optional> }`.
  - Task missing → 404 `task_not_found`.
  - `body` empty or whitespace-only → 422 `validation_error`
    (contract envelope, no echo of the submitted value).
  - `supersedes_id` naming a comment that does not exist, or that
    belongs to a different task → 404 `comment_not_found`
    (existence is not leaked across tasks).
  - `supersedes_id` naming a revision that has already been
    superseded → 409 `conflict`: a revision must supersede the
    current head of its chain, so chains never fork.
- `GET /v1/tasks/{task_id}/comments` → the full revision log for the
  task in id order, cursor-paginated exactly like `GET /v1/tasks`
  (`{ "items", "next_cursor" }`, same clamping). Task missing → 404
  `task_not_found`.
- `GET /v1/tasks/{task_id}/comments/{comment_id}` → one comment;
  missing task → `task_not_found`; missing or cross-task comment →
  `comment_not_found`.
- Comment shape: `{ "id", "task_id", "body", "supersedes_id" }`.
- A down store answers 503 `store_unavailable` on the new routes
  too (the central `sqlite3.Error` handler already covers this —
  pin it with a test, following the existing down-store tests).
- Tests for all of the above, including a v1 → v2 → v3 revision
  chain and list pagination. Docs and the OpenAPI spec are updated
  after this merges (they must not claim the endpoints early).
