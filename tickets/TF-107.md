## Problem

`taskflow-api-docs/openapi.yaml` is the curated, published contract
for demo-app (GitBook republishes it as the interactive reference).
It is maintained by hand, and it has already drifted once:
`endpoints.md` marked two task operations as demo-implemented when
they were not, and the error catalog missed a code the app actually
returns. Both were caught by a human, late. The app and its spec are
the two halves of the workspace's central promise — documentation
the code actually honors — and nothing currently verifies them
against each other.

## Scope (demo-app)

- New `tests/test_spec_conformance.py`: a behavioral conformance
  suite driven by the spec itself.
  - **Route parity:** the spec's paths and methods equal the app's
    own route set (from `app.openapi()`), in both directions — an
    undocumented operation and a spec operation the app does not
    implement are both failures.
  - **Success shapes:** for every operation, a scripted scenario
    (keyed by `operationId`, following the existing tests' fixture
    style) runs against a migrated throwaway store via `TestClient`;
    the response status must be the operation's declared success
    code, and the body must validate against the referenced schema
    (a small in-test validator for the schema subset in use: `$ref`
    into `components`, object/array/string/integer types,
    `required`, `properties`, `items`, `nullable`, `enum`).
  - **Documented errors:** the catalogued failure scenarios (missing
    task, missing or cross-task comment, stale revision `conflict`,
    `invalid_status`, blank-body `validation_error`) return statuses
    the spec declares for that operation, with bodies matching the
    `Error` schema.
- Spec location: the `TASKFLOW_SPEC_PATH` environment variable,
  defaulting to the workspace sibling
  `../taskflow-api-docs/openapi.yaml` (relative to the repo root).
  When no spec file is present the suite skips with a clear reason —
  a bare clone of demo-app must not fail — while CI always provides
  the file, so the check is binding there.
- CI: a new `spec` job in `.github/workflows/tests.yml` downloads
  the spec from the public `taskflow-api-docs` raw URL, sets
  `TASKFLOW_SPEC_PATH`, and runs only the conformance file.
  `pyyaml` joins `requirements-dev.txt`.
- The curated spec stays curated (descriptions, the error-schema
  substitutions): this ticket tests behavior and shapes, not text
  equality with `app.openapi()`.

## Resolution (2026-11-12, demo-app PR #9, merged)

demo-app carries `tests/test_spec_conformance.py` (21 cases): route
parity in both directions against `app.openapi()`, one scripted
scenario per operation validated against the published spec's
schemas, and the documented error scenarios checked for declared
status and the `Error` envelope. The suite resolves the spec from
`TASKFLOW_SPEC_PATH` or the workspace sibling and skips cleanly
when no spec is present. CI gained a `spec` job that downloads the
published spec and runs the suite; its first live run was PR #9's
own Actions (all four jobs green). Review verdict: approve, no
findings. Negative checks: removing `get_comment` from a spec copy
fails 6 cases; mistyping `Comment.body` fails 3.
